## canonical_production_epoch_contract

- Phase 069 has one production Plonky3 publication path: for each exact
  consecutive range of `2000` finalized checkpoint blocks, emit exactly one
  canonical recursive epoch proof envelope. Plan 07 supplies the full base
  theorem and bounded recursive building block; Plan 08 owns the exact
  `2000`-block epoch aggregation and inherits this contract without
  reinterpretation.
- Plan 07 applies the same `2 MiB` target to one complete canonical
  single-transition base-theorem envelope as a prerequisite. Plan 08 MUST
  recursively aggregate exactly `2000` such transitions into a final
  per-epoch payload that also targets at most `2 MiB`; the allowance never
  multiplies by the leaf count.
- The production size target is `2,097,152` bytes (`2 MiB`) for the complete
  canonical encoded per-epoch Plonky3 payload. The measurement includes every
  transcript-separated root/replica, recursive proof body, public input,
  manifest field, and required framing. It is not a separate allowance for
  each root, leaf, chunk, or history proof body, and transport compression does
  not count toward compliance.
- The finite publication cap is `4,194,304` bytes (`4 MiB`) for that same
  complete payload. A verified envelope in `(2 MiB, 4 MiB]` is publishable
  degraded evidence with
  `Plonky3ProofSizeStatusV2::TargetMissed`; it preserves recursive/history
  liveness but cannot satisfy the Plan-07 or Plan-08 size acceptance gate.
- Raw base proofs, chunk proofs, and intermediate recursion nodes are bounded
  ephemeral prover artifacts. They MUST NOT be published as the epoch result,
  retained as permanent history, or used to split one epoch into multiple
  final envelopes to evade the `4 MiB` publication cap. An internal node may exceed
  `2 MiB` within its separate resource-safety bound and continue through
  additional sound recursion; the production limit is evaluated only on the
  one complete canonical output.
- `16 MiB` is only the untrusted-input parser/allocation and DoS emergency
  ceiling before the input type is trusted. Once identified as a canonical
  Plonky3 V2 proof, any payload larger than `4 MiB` is rejected before
  proof-specific allocation, deserialization, or verification as
  `ProofSizeBudgetExceeded`; a payload above `16 MiB` rejects at the generic
  ingress guard.
- The Phase-069 production acceptance fixture is exactly `2000` finalized
  blocks (`10,000` seconds, or `2 h 46 min 40 s`, at the configured five-second
  finalization interval). A smaller smoke-test range, a different cadence, weaker security
  parameters, or multiple published proof objects cannot be used to claim
  production acceptance. If the real proof cannot satisfy the theorem,
  security, memory, and total encoded-size limits together, the owning plan
  remains `BLOCKED` and records stop/split evidence.
- `ProofSizeBudgetExceeded` above `4 MiB` is fail-closed for the Plonky3 publication branch,
  not a process panic or canonical-chain failure. Because this branch is
  asynchronous and non-authoritative, canonical checkpoint finality and Nova
  folding continue while the epoch remains in the bounded pending-PQ queue.
  Once the configured pending limit is reached, new compression/publication
  work stops according to
  `stop_compression_publication_keep_fold_finality`; the implementation MUST
  not drop epochs, bypass the size cap, or reinterpret an oversized object as
  verified evidence.

## 🚨 Resource Safety and Memory Acceptance Contract

This contract is a mandatory Plan-07 acceptance boundary, not an optional
profiling recommendation.

### Incident authority

- The real `test_recursive_v2_plonky3_base` process reached approximately
  `51.7 GiB` anonymous RSS and was killed by the Linux OOM killer.
- The process ran inside the VS Code systemd scope whose `OOMPolicy=stop` and
  `KillMode=control-group` terminated the whole editor.
- The current host has no swap.
- `24 GiB` is an emergency safety ceiling. It is neither an allocation target
  nor permission to require a 64 GiB host.

### Mandatory execution boundary

1. An unchanged command that reaches OOM, `SIGKILL`, cgroup `MemoryMax`, or the
   resource timeout MUST NOT be rerun automatically. The run ends the current
   implementation attempt and emits typed `resource_exhaustion` evidence.
2. The executor MUST NOT create or enable swapfile, zram, zswap, change sysctl
   settings, change the VS Code scope, or modify global systemd OOM policy.
   Swap is diagnostic-only after explicit user approval, must be encrypted and
   finitely capped, and a swap-assisted run can never satisfy Plan 07.
3. Every real Plonky3 prover test MUST run in a separate transient worker unit
   outside the VS Code application scope. On systemd/cgroup-v2 hosts the worker
   uses `OOMPolicy=continue`, `MemoryHigh=16G`, `MemoryMax=24G`, and
   `MemorySwapMax=0`. If these controls are unavailable, an equivalent
   container/CI cgroup is required; the executor MUST fail closed rather than
   silently run without isolation. The heavy unit MUST be detached from the
   invoking editor/exec client: launcher termination cannot stop the unit or
   erase its terminal evidence. A durable `run-state.json` is written before
   launch, the worker writes its own `resource-evidence.json`, and `--status`
   or `--status-latest` can recover the result after launcher loss.
4. Only one named heavy proof test may run at a time, always with
   `--test-threads=1`. Always-on bounded smoke, codec, parser, manifest,
   mutation, and fail-closed tests remain separate from real heavyweight prover
   acceptance. Both real targets are `#[ignore]` in ordinary Cargo suites and
   the isolated worker selects one exact ignored test explicitly.
5. Every worker records wall time, peak RSS, cgroup `memory.events`, exit
   reason, fixture identity, backend/parameter digests, trace dimensions, and
   phase-level memory high-water marks under
   `crates/z00z_storage/outputs/checkpoint/069-07/`. Witness bytes MUST NOT be
   logged.
6. Resource budgets are:
   - regular smoke-test process: at most `4 GiB` peak RSS;
   - one real base-proof target: at most `16 GiB` peak RSS;
   - absolute emergency ceiling: `24 GiB`;
   - supported dedicated prover host: `32 GiB` RAM with OS/service headroom.
