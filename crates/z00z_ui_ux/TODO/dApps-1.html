1. Use case

BOLD on Ethereum

     routing
        ↓

Пример документа:

2. Wallet feature

В кошельке это функция:

Swap
Exchange
Bridge
Buy/Sell

Она отвечает за UX:

  • выбор to asset;

  • fees;

  • срок действия quote;

Hyperliquid, внешний DEX, Ethereum AMM или другой рынок — это источник ликвидности или execution venue.

├── Hyperliquid adapter

Hyperliquid не должен находиться в:

Правильнее:

integrations/hyperliquid/

или:

packages/liquidity-venues/hyperliquid/

Что должно лежать в swap-core

swap-core не должен знать детали конкретного DEX.

Он должен работать через общий интерфейс:

Rust
pub trait SwapProvider {
    fn get_quote(&self, request: QuoteRequest) -> Result<Quote>;
    fn build_order(&self, quote: Quote) -> Result<SwapOrder>;
    fn submit_order(&self, order: SwapOrder) -> Result<OrderId>;
    fn get_status(&self, order_id: OrderId) -> Result<SwapStatus>;
}

Реализации:

NearIntentsProvider
HyperliquidProvider
EthereumDexProvider
DirectSolverProvider

Тогда кошелёк делает:

Wallet Swap UI
      ↓
swap-core
      ↓
provider interface
      ↓
NEAR Intents / DEX / solver

А не:

Wallet UI → напрямую Hyperliquid API
Wallet UI → напрямую NEAR API
Wallet UI → напрямую Uniswap

Иначе кошелёк быстро превратится в набор жёстко связанных интеграций.

Как должен выглядеть общий Swap flow

1. Пользователь выбирает:
   BOLD → Z00Z

2. Wallet создаёт QuoteRequest

3. Swap Router запрашивает варианты:
   - NEAR Intents
   - direct solver
   - Ethereum DEX + bridge
   - другой liquidity provider

4. Router сравнивает:
   - конечную сумму
   - fees
   - slippage
   - execution time
   - trust assumptions
   - settlement risk

5. Пользователь выбирает quote

6. Wallet показывает полный маршрут

7. Пользователь подписывает

8. Execution provider выполняет маршрут

9. Wallet отслеживает статусы

Важно показывать не только цену, но и какой маршрут используется:

Route: BOLD on Ethereum → NEAR Intents solver → native Z00Z

Expected output: 982 Z00Z
Minimum output: 970 Z00Z
Estimated time: ...
Provider fee: ...
Ethereum gas: ...
Custody model: temporary solver settlement

Нужно ли выделять Exchange отдельно от Swap

Я бы не делал две почти одинаковые функции.

В UI:

Swap

А внутри неё:

  • same-chain swap;

  • cross-chain swap;

  • intent-based exchange;

  • bridge-and-swap;

  • RFQ;

Термин Exchange часто создаёт впечатление полноценной биржи:

  • user accounts;

  • deposits;

  • trading history;

  • limit orders.

Если Z00Z не управляет биржей, лучше называть функцию:

Swap

или:

Swap & Convert

а не:

Z00Z Exchange

Как классифицировать в каталоге dApps

В каталоге можно показать Swap как приложение:

Z00Z Apps
├── Pay
├── Swap
├── Vouchers
├── Access
├── Payroll
└── Agents

Но это продуктовая классификация.

В технической архитектуре:

Swap = wallet feature or standalone frontend
NEAR Intents = execution provider
Hyperliquid = liquidity venue
DEX = liquidity/execution venue
Solver = execution participant
BOLD = settlement asset

Моя рекомендация для Z00Z

Сделать два уровня.

В кошельке

apps/wallet/features/swap/

Пользователь видит обычную вкладку Swap.

Общий reusable engine

packages/swap-core/
packages/intent-core/

Он может использоваться:

  • Wallet;

  • web dApp;

  • merchant app;

  • external partners;

  • mobile app;

  • agent wallet.

Внешние системы

integrations/near-intents/
integrations/hyperliquid/
integrations/ethereum-dex/
integrations/liquity-bold/

Документация сценариев

docs/use-cases/swap/

Итог

Swap можно считать dApp на продуктовом уровне, особенно если он доступен как самостоятельный web-интерфейс.

Но в структуре кода правильнее разделить:

dApp / Wallet feature:
Swap UI

Core:
swap-core + intent-core

Execution:
NEAR Intents

Liquidity:
Hyperliquid / DEX / market makers

Settlement assets:
BOLD / ETH / Z00Z

Documentation:
Swap use cases

Поэтому не следует складывать всё это в один каталог dapps/swap. Лучший вариант:

apps/wallet/features/swap
packages/swap-core
integrations/near-intents
integrations/hyperliquid
docs/use-cases/swap

Так Swap остаётся видимым dApp-сценарием для пользователя, но внешние протоколы и liquidity venues не смешиваются с приложением.
